For the below, package names are Ubuntu.

Package `shim-signed` in Ubuntu contains the signed `shim` bootloader.

The files installed that we need to get into the `/boot/efi` are:

    /usr/lib/shim/shimx64.efi.signed <- actual `shim` bootloader.
    /usr/lib/shim/mmx64.efi <- MOK ("Machine Owner Key") Manager binary.
    /usr/lib/shim/fbx64.efi <- Fallback bootloader.

`shim` has a concept of Machine Owner Key, i.e. a key that the owner of
the actual machine uses to sign binaries that will be loaded later.
The MOK is installed into NVRAM, but is technically separate from the
firmware-trusted keys.

Instead, the firmware trusts the signed `shim` EFI binary, then the `shim`
trusts the second bootloader if it is itself signed with a firmware key,
or with a Machine Owner Key.

The fallback bootloader is used if `shim` can't find the second bootloader.
The fallback bootloader will look for `BOOT.CSV` files in other
sub-directories of the EFI boot partition (`esp`).
This `BOOT.CSV` would then be used by the fallback loader to add a new
entry to the EFI.

The `shim` bootloader uses fixed filenames in the same directory.
On AMD-64 those are:

    grubx64.efi <- the second bootloader to use (replace with ZfsBootMenu!)
    mmx64.efi <- the MOK Manager binary above.
    fbx64.efi <- the fallback bootloader.

In particular, `grubx64.efi` ***MUST*** be signed, either by a firmware key,
or by some registered MOK.
This is the second bootloader.

The expected layout of the `esp` is like this:

    # These are the "fallback" path bootstrap when the EFI list
    # in the firmware is not populated or missing.
    \EFI\BOOT\bootx64.efi <- `shim` from `shimx64.efi.signed`
    \EFI\BOOT\mmx64.efi
    \EFI\BOOT\fbx64.efi

    \EFI\ZFSBootMenu\shimx64.efi <- `shim` from `shimx64.efi.signed`
    \EFI\ZFSBootMenu\mmx64.efi
    \EFI\ZFSBootMenu\grubx64.efi <- actually ZfsBootMenu EFI, but SIGNED by some MOK
    \EFI\ZFSBootMenu\BOOTX64.CSV

Then the `BOOTX64.CSV` file contains the following, except in UCS-2 little-endian
format (use `iconv -t UCS-2 < input > output` to convert):

    shimx64.efi,ZFSBootMenu,,This is the boot entry for ZFSBootMenu

In case the EFI entries are erased, the fallback bootloader `fbx64.efi`
will read the `\EFI\ZBM\BOOTX64.CSV` file and regenerate the boot entry
for ZFSBootMenu.

Installing `shim-signed` on Ubuntu creates one MOK ("Machine Owner Key") located here:

    /var/lib/shim-signed/mok
    /var/lib/shim-signed/mok/MOK.priv <- private signing key
    /var/lib/shim-signed/mok/MOK.der <- DER format of the certificate, for uploading with mokutil

The above MOK has a 100-year lifetime, which is good enough for most purposes.

The `MOK.priv` file is also only readable by `root`.

***HOWEVER***, this key is specifically only created for *kernel module
signing*.
Specifically, the `openssl.cnf` for it contains:

    # codeSigning:  specifies that this key is used to sign code.
    #
    # 1.3.6.1.4.1.2312.16.1.2:  defines this key as used for module signing
    #                           only. See https://lkml.org/lkml/2015/8/26/741.
    #
    extendedKeyUsage        = codeSigning,1.3.6.1.4.1.2312.16.1.2

The above link shows the rest of the OIDs defined for Linux:


            1.3.6.1.4.1.2312.16     Kernel OIDs
            1.3.6.1.4.1.2312.16.1   - X.509 extendedKeyUsage restriction set
            1.3.6.1.4.1.2312.16.1.1   - Firmware signing only
            1.3.6.1.4.1.2312.16.1.2   - Module signing only
            1.3.6.1.4.1.2312.16.1.3   - Kexecable image signing only
            1.3.6.1.4.1.2312.16.1.4   - 802.11 regulatory data
            1.3.6.1.4.1.2312.16.1.5   - SELinux policy signing only

However, we also need to be aware of the following OID:

            1.3.6.1.4.1.311.10.3.6

Which is a Microsoft OID, apparently described as "Windows system component
verification (signed by the "NT5" build lab) (szOID_NT5_CRYPTO)", and is in
the Microsoft namespace.

From what I can tell, 1.3.6.1.4.1.311.10.3.6 is used for signing EFI images.

I am uncertain what happens if you add both module signing and EFI signing.
I have seen a reference that claims that giving both the above Microsoft
EFI signing OID and the Linux module signing only OID will cause kernel
module validation to fail, but I haven't tried it seriously.

On the other hand, I do know for a certain fact that not providing an
`extendedKeyUsage` during MOK creation will create a key that can be used
to sign both EFI images and kernel modules; I did this in my initial
install for a SecureBoot environment.
The `shim` `README.md` suggests that it replaces the normal validation
entry points (`LoadImage`/`StartImage`) with its own, so that it can also
allow kernel module signatures and kernel images validation against the
MOK.

Finally, I know for a certain fact as well that a key *with* the Module
Signing Only OID will *not* be respected for EFI images.

This leads me to consider that we should ***NOT*** include the
`extendedKeyUsage` entry and instead use a key without it!
This seems to create a key that can be used to sign the
ZFSBootMenu bootloader, the kernel `vmlinuz`, ***and***
`.ko` kernel modules.

On Debian, the MOK created supposedly is located at:

    /var/lib/dkms/mok.key <- private key
    /var/lib/dkms/mok.pub <- public key, in DER format

Though I don't think I've seen it in my Trixie virtual machine.

I don't know if, like with the Ubuntu situation, this is a
module-signing-only key, but we should probably generate a
MOK that can sign for EVERYTHING.

Another complication is that the default `shim-signed-common` process
that creates `/var/lib/shim-signed/mok` only creates `MOK.der`, but
the `sbsign` utility needs `MOK.pem` i.e. the PEM format.
We... probably should override the `shim-signed` MOK, really.

MOK Manager

We can install the `mokutil` package to interact with the MOK Manager EFI binary.
This installs the `mokutil` utility.

The `mokutil` can be used to install the `.ko`-signing `MOK.der` file by:

    mokutil --import /var/lib/shim-signed/mok/MOK.der

The importation of the MOK will actually complete in the next reboot; the
user has to manually manipulate the UI of the MOK Manager binary.
The issue here is that this will require a password input from the user;
on reboot, if you install the key that is imported, the user must re-enter
the password.

Alternatively, we can add the `MOK.cer` file into the `esp`; the user still
has to manually enter into MOK Manager (which `shim` will normally do if
the second bootloader is signed, but `shim` can't find the firmware key
or MOK that signed it), but at least a password isn't necessary in that
case.
This has to be DER format.

Since we want to have an encrypted pool anyway, we can reuse the pool
password here.
`mokutil --import` accepts an option `--hash-file`, which contains the
hash of the password.
We can generate the password hash from a shell variable by:

    mokutil --generate-hash=${PASSWORD} > the-hash-file

That way, the password used in MOK Manager is something the script can
prompt or otherwise get into its shell variables.

We need to then download the ZfsBootMenu EFI from https://get.zfsbootmenu.org/efi and
rename it to `grubx64.efi` in the `\EFI\ZBM\` directory of the `esp`.

This is a completely unsigned binary.
Apparently it used to be signed by the ZfsBootMenu team (which had an OpenSSL pubkey
that you could add as an MOK), but this is no longer done and you are instead
supposed to sign it with your own local MOK.

To sign, we must install `sbsigntool`, which installs `sbsign` and `sbverify`.
`sbsign` needs the private key and certificate of the MOK you want to use, and
generates a copy of the EFI binary being signed.

Validating ZFSBootMenu

We need to find who we can trust to acquire ZFSBootMenu for us.

The link https://get.zfsbootmenu.org/efi only downloads the ZFSBootMenu EFI.
We still need the signatures and public key.

We should hardcode the public key.
The `signify` public key is tiny and can be embedded in the script itself.

    untrusted comment: ZFSBootMenu signing key public key
    RWSUawlGznCLF8NxEb1EyrGpP2eIR9l7JIZgLzCdv+64uBDvfXNJm+cF

The signature can be acquired from https://get.zfsbootmenu.org/sha256.sig .

There is a theoretical race condition here when a new ZFSBootMenu is released;
whichever one we fetch first, might be the older version and then we fetch
the newer version of the other file.
This is probably unlikely to occur however.

The documentation describes how to validate:

    signify -C -x sha256.sig -p /path/to/zfsbootmenu.pub

And I discovered, to my horror, that the `signify` package on Ubuntu does
***not*** actually match this tool; it's a different "tool" that creates
random messages from files for no reason.
Yay!

Instead, we should install `signify-openbsd`, which installs the tool
`signify-openbsd`.
However, we should note that Void Linux apparently has `signify` instead, and
if we want to include that as a possible Boot Environment for this tool, we
do need to figure out which one is installed.

Another complication is that `curl` and `wget` by default will save to a file
named `efi` instead of the original filename, which is what the `sha256.sig`
file indicates.
We can suppress this with `wget`:

    wget --content-disposition https://get.zfsbootmenu.org/efi

This will download and put it in the filename indicated by the server.
The problem is that this doesn't really have a good way for us to discover
the actual file name --- what we can do is to create a temporary directory
(which would then be empty) and then `wget` the file into it, and list the
only file in that directory.

and `mok_certificate`.
These should point to the path to the mok private key and certificate.

They can be put in a file in `/etc/dkms/framework.conf.d`

However, recent Debians don't need it (and in fact there were already
deprecation warnings for that flag) and it can be left out.

Swap

Ideally if we are encrypting anyway, we should include the swap in the encryption.
If this were a LVM tank, then the entire tank could have a LUKS encryption and
then the swap would be a volume within the LVM tank.

Unfortunately, ZFS itself needs to allocate memory while it is writing to disk,
and that means that a swap file in a ZFS dataset or a swap partition on a `zvol`
can trigger this memory allocation while the kernel is busy swapping out memory.
(This is less likely to occur with `zvol`s configured for througput and simplest
compression `zle` or `off`, but apparently it is possible to write C programs
that can still trigger this deadlock even with such configurations)

https://github.com/openzfs/zfs/issues/7734

There are guides on the Internet for using `zvol` swap partitions, but the
above issue points out that even as of this writing (October 2026) the crash
still exists.
The various configurations floating on the Internet might lower the probability
of deadlocks, but doesn't actually remove it from the codebase.

This probably means swap is not useable on ZFS on other kernels either, like
BSD or Solaris.
Honestly, the correct behavior should probably be to *not* have swap and
use the ZFS ARC as the "swap", i.e. force ZFS to drop its ARC entries on
memory pressure.

What we can do instead would be to give the option to put
some swap partition on *every* disk in the array.
Since you will likely buy multiples of the same drive anyway,
and ZFS doesn't really support having different sizes in
the same VDEV, there's no point in having one drive lose
some space for swap while the other disks have full space
after the ESP; ZFS will treat all disks as having the
swap space removed anyway.
At least if we add a swap partition on every drive we
can switch to a different swap partition if the drive
hosting it dies.
Then, we create an encryption key for the swap volume and
store it in the ZFS pool --- this has the same protection
as keeping the MOK in the ZFS Pool without a passphrase
anyway.
This should still allow for resume, since the ZFS Pool
is unlocked already on booting into the kernel and we
can decrypt the swap.

The big problem of course is that making the swap volume
match memory size means we can't, in practice, increase
installed memory, at least not easily, heh.

Honestly it would be nice if you could just enable
hibernation into some volume without making that
volume a swap for normal operation.
See this for a hack that emulates it by turning off
swap most of the time, but turns it on when triggering
hibernation and getting out of it:

* https://superuser.com/questions/1147616/hibernation-without-swap-enabled

Keyrings

Because APT classically used http, which allows MITM,
it is entirely possible for repositories to be subverted.
To protect against this, APT uses signatures from trusted
PGP keys.

If `debootstrap` fails to find a keyring in
`/usr/share/keyrings`, it will fall back to an HTTPS
archive, either `https://deb.debian.org/debian` or
`https://archive.ubuntu.com/ubuntu` depending on the
script.

However, if you pass in an http mirror explicitly,
`debootstrap` will completely trust the repository.
Thus, for cases where the distro needs an http mirror,
we should provide the keyring to trust for that distro.

(generally, we actually do want the keyring to exist in
general so that we can validate `Release`)

We can manually get the keyring, export all of it to an
armored ASCII file, then embed the file in the script.
When installing a distro, we write out the embedded
armored ASCII file, then create an empty keyring and
import the armored ASCII file to regenerate a keyring
we can use.
We can then pass the keyring directly into `debootstrap` via
`--keyring`.

Convert to armored ASCII:

    gpg --keyring ./foo.gpg --no-default-keyring --homedir /dev/null --export -a > foo.asc

Import armored ASCII to empty keyring:

    gpg --keyring ./empty.gpg --no-default-keyring --import ./foo.asc

ISO-squashfs Install Path

It turns out we can get many distro's Live CD .iso
file and use it to install into the ZFS Pool directly.
We do this by simply extracting the initial-install
files from the Live CD and putting them into the
ZFS Pool.

Note that for the most part, once it's on a Unix-enough
filesystem (like ZFS) it doesn't actually matter too
much HOW the files in the system got there.
In fact, that's what most installers are, they have one
or a few .squashfs files in the .iso.
Usually it's just `filesystem.squashfs`, in a directory
called `casper` (Casper being a system that creates a
Linux filesystem in memory to serve as the root filesystem
for the Live CD).

On installing, the Live CD installer will format and
partition the machine-installed storage, mount a root
filesystem, then expand the .squashfs file into it.
Then they might do some additional things --- the
equivalent of
`dpkg-reconfigure locales keyboard-configuration tzdata`
et al --- flash the ESP, and call it a day.

For Slimbook OS, there are three .squashfs:
`filesystem.squashfs`, `filesystem.plasma.squashfs`, and
`filesystem.gnome.squashfs`.
It seems likely they use just `filesystem.squashfs` and
`filesystem.gnome.squashfs`.

Most OSs will use `filesystem.squashfs`.

This is a major unlock, because it greatly reduces the
pain of having to support new distros, and especially
new releases of the same distro.
Often there will be a change in the list of packages
that are installed between releases.

With the ISO-squashfs path, updating to new release
versions is much easier: we don't need to track the
list of packages to be installed to make the distro
"complete".
All we need is to just add the packages needed to
get the ZFS module.

There are some complications, of course, because
nothing is ever easy.

* We need to hardcode the ISO-signing key for each
  supported distro and validate the ISO we download
  has been signed with the key.
* DKMS!
  - If the Live CD .squashfs already contains DKMS
    modules, those will be in binary form and
    *unsigned*.
  - We need to force recompiling the DKMS modules
    after we have set DKMS to sign with our MOK,
    possibly by iterating over all DKMS modules
    and kernels (`dkms status` output, basically).
    - Actually we *don't* need the recompile part,
      we "just" need the modules signed.
      But that will make the DKMSS status dirty
      as it will say there is a difference between
      built and installed version.
    - Looking at DKMS source code, it signs at
      the end of building, so we need to force
      building AND installing.
      Building takes a long time, but that's
      much safer than poking into DKMS's build
      directory and the kernel's module directory.
      - Complications abound here: if it's xz
        format we must explicitly use crc32,
        we need to extract the hash function from
        the kernel config, we need to know the
        structure of the build dir, sigh...
        Yeah these days kmodsign exists but
        the rest of DKMS is still a mess.

But in any case, our process becomes:

* We need a new pre-install subcommand for distro
  (noop on existing supported distros).
  - pre-install: download ISO file, extact squashfs.
    (we need to mount the ISO file to extract
    files inside it and we want to simplify things
    for users who abort zfsbootmenu-installer by
    just having $WORKDIR/mnt as the only point to
    umount -qnR)
* install-outside: expand squashfs into the target
  dir.
* install-chroot:
  - Setup DKMS and kernel signing.
    - debian-derivative-prepare
  - Rebuild any existing DKMS modules.
    - Iterate over `dkms status` output which
      outputs one line for every
      module/version, kerversion pair.
      Maybe be careful about ", added" lines
      which do not have kerversion.
  - Set up keyboard-configuration, locale, timezone.
    - `dpkg-reconfigure keyboard-configurtion locales tzdata`
  - Install ZFS kernel module.
    - The most likely to work across all distros
      and across distro releases is just to
      download ZFS from source and build, but
      that's longer than using `zfs-dkms` if
      available.
  - Enable ZFS support.
    - debian-derivative-install-chroot-zfs-support
    - Includes zfs-auto-snapshot, which we
      have to download ourselves if not available.
  - Enable ZFS services and rebuild initramfs.
    - debian-derivative-install-chroot-zfs-config
  - Make the user
    - debian-derivative-install-chroot-make-user
  - Enable auto-login
    - typical-enable-auto-login
  - Do distro-specific final stuff, like
    Slimbook OS needing to install device-specific
    meta packages.

We don't even need to sign kernels since the outside
install-distro-core does that.

Note that the distro-specific stuff here is much
smaller:

- Distro dev keys (likely valid across releases)
- ISO and its validation (likely similar across
  releases)
- how to install ZFS (likely the same across
  releases)
- Distro-specific final stuff (likely the same
  across releases)
